# OperationBudgetLedger v1

Status: normative for SP0 and the explicitly named GEN0 profiles. It limits
deterministic semantic work, not wall time, memory, or implementation
instruction count.

## State and reservation

Counters are checked unsigned 64-bit integers. An action executes only after
atomically reserving its charge. Equality with a ceiling succeeds; overflow or
`used+charge>ceiling` fails without changing counters or producing a partial
Project. Each leaf reservation mirrors the same amount into
`total_logical_units` in that transaction.

CompilerManifest, not SongProgram, owns the profile; its digest is part of
compiler identity. SP0 ceilings are:

```text
structural_items 100000; placed_domain_points 4096
exact_arithmetic_units 500000; numeric_eval_units 100000
chord_search_nodes 250000; pair_relations 1000000
ordering_units 500000; validation_items 100000
emitted_events 2048; total_logical_units 2500000
```

Each content-addressed chord-query child has ceilings 50000 search nodes,
200000 pair relations, and 20000 numeric units. Child, root-leaf, and root-total
checks update atomically. Children are created in canonical query-ID order;
nesting deeper than one is forbidden.

The `gen0-progression-exact-v1` profile retains every ceiling above and adds:

```text
progression_states 12288; progression_edges 294336
```

These are the exact schema maxima: `512*24` candidate states and
`511*24*24` adjacent-layer candidate pairs. One content-addressed progression
query owns one child with the same state/edge ceilings. Its child ID is
`progression_` followed by the first 16 lowercase hex digits of the canonical
query SHA-256. The child leaf, root leaf, and root `total_logical_units` checks
succeed or fail in one transaction; equality succeeds. There is no nested
per-occurrence child.

## Normative charges

- `structural_items`: one per normative parsed node, symbol insert/reference,
  timeline item, realization instance, rhythm step, transform-step,
  interaction-event examination, or material-instance record.
- `placed_domain_points`: one per `(vector,equave exponent)` before deduplication.
  Exact SP0 reserves the entire placed cardinality before enumeration.
- `exact_arithmetic_units`: use only the opcodes below. Let
  `L(x)=max(1,bit_length(abs(x)))` and `W(x)=ceil(x/64)`. Fraction operands are
  reduced before the opcode. Each opcode costs 1 plus `W` of every operand
  component plus `W` of the stated unreduced upper bound: `FRAC_MUL(a/b,c/d)`
  bounds numerator `L(a)+L(c)`, denominator `L(b)+L(d)`; `FRAC_DIV` bounds
  `L(a)+L(d)`, `L(b)+L(c)`; `FRAC_POW(a/b,k)` bounds numerator and denominator
  by `max(1,abs(k)*L(component))`, swapping them for negative k and rejecting
  zero base with negative k; `FRAC_COMPARE` has result bound 1; `FRAC_REDUCE`
  takes unreduced integers and has result bounds `L(n),L(d)`. `VECTOR_ADD` and
  `VECTOR_COMPARE` cost `1+sum(W(L(component)))` over both vectors and have no
  result term. No implicit arithmetic action exists: ratio construction must
  emit its prescribed opcode sequence even when optimized or cached. Any
  stated bound over 4096 bits fails `ARITHMETIC_COMPLEXITY_EXCEEDED` before
  execution.
- `numeric_eval_units`: ratio/log2 conversion 16; EDO target 8; integer pair
  error 1; RMS `4+pair_count`. NumericContract precision escalation adds no
  logical charge.
- `chord_search_nodes`: one for root, every partial assignment, and every
  complete assignment, including immediately rejected trials.
- `pair_relations`: one per unordered relation evaluated when adding a voice.
- `ordering_units`: sorting length `n` reserves 0 if `n<=1`, otherwise
  `n*ceil(log2(n))`; top-K insertion costs `ceil(log2(K+1))`.
- `validation_items`: one for each invocation of exactly one opcode:
  `VALIDATE_COLLECTION_MEMBER`, `VALIDATE_REFERENCE`, `VALIDATE_EVENT_BOUNDS`,
  `VALIDATE_EVENT_ROLE`, `VALIDATE_PROVENANCE_EQUATION`,
  `VALIDATE_REGISTER_RANGE`, `VALIDATE_CHORD_VOICE`, `VALIDATE_CHORD_PAIR`,
  `VALIDATE_HASH_CORE_MEMBER`, `VALIDATE_CANONICAL_ADJACENCY`. A validator emits
  these logical opcodes in Project-contract validation order regardless of
  batching or library internals.
- `emitted_events`: one before event creation; it equals final event count.
- `progression_states`: one per candidate in every progression layer, reserved
  in occurrence order then frozen candidate order before hard constraints.
  Rejection does not refund it.
- `progression_edges`: one per Cartesian predecessor/current candidate pair in
  adjacent layers, reserved in predecessor order then current-candidate order
  before matching enumeration. Invalid or unreachable endpoints and an empty
  matching set do not refund it.

Each normative action charges exactly one leaf counter. Cache hits replay the
canonical charge receipt, yielding the same usage and outcome as a miss.

## Normative logical program

Charges are generated by this logical program, irrespective of implementation:

1. Traverse canonical JSON depth-first in object-key byte order and array order;
   emit one `structural_items` for every object, array, and scalar node.
2. In compiler-pass order, traverse each ID-sorted symbol collection; emit one
   structural item per insert, then one per scalar ID reference in canonical
   field/array order. Emit one per form item, realized repeat, source step,
   transform/source-step Cartesian pair, interaction/relevant-event Cartesian
   pair, and material-instance record, in that order.
3. For each distinct domain digest in byte order, reserve its complete placed
   cardinality once. Enumerate vectors lexicographically, exponent ascending.
4. Exact `VECTOR_RATIO(v,k)` starts at reduced 1/1; for each generator ordinal
   emits `FRAC_POW(generator,v[i])`, then `FRAC_MUL(acc,power)`; finally emits
   `FRAC_POW(equave,k)` and `FRAC_MUL`. Fraction opcode outputs are reduced, so
   no separate reduce opcode follows. `PAIR_RATIO(i,j)` emits exactly one
   `FRAC_DIV(rj,ri)`. `EQUAVE_REDUCE(q,E)` repeatedly emits one `FRAC_DIV(q,E)`
   while `q>=E`, or one `FRAC_MUL(q,E)` while `q<1`, testing with one
   `FRAC_COMPARE` before each iteration and once on exit. Vector source equations
   emit one `VECTOR_ADD` per written `+`, left to right. Numeric functions then
   emit their fixed NumericContract charge once per call.
5. Chord queries run in query-ID order. Candidate vectors use domain order;
   target assignments use lexicographic permutation order. Reserve a search node
   before testing it and pair relations in canonical `i<j` order. Stop checking
   that node at its first hard rejection in NumericContract order, but SP0
   exhaustive search performs no branch pruning and continues with every sibling
   partial and complete Cartesian assignment.
6. Emit events in semantic-address order, charging immediately before creation.
7. Validate in the Project-contract order. For every collection member emit
   `VALIDATE_COLLECTION_MEMBER`; every scalar ID reference emits
   `VALIDATE_REFERENCE`; each event emits, in order, bounds, role, provenance
   equation, and register opcodes (drums omit the last two); each chord emits one
   chord-voice opcode per voice, one chord-pair opcode per `i<j`, and one
   hash-core opcode per listed core field; each canonically ordered collection
   emits one adjacency opcode per adjacent pair. Stop at the first failure.
8. For a progression query, reserve state actions and adjacent-layer edge
   actions at their prescribed evaluation positions. The state/edge action is
   the leaf charge; injective matching enumeration adds no separate opcode.
   Stop at the first failed atomic reservation.
9. Apply each required sort charge once, immediately before that logical sort.

This algorithm is the prescribed opcode stream for every input. Memoization,
batch validation, balanced multiplication, parallelism, and library callbacks
must replay the same logical receipt. Parsing failure stops after the offending
canonical traversal node; later phases emit nothing.

## Domain preflight

With checked unsigned 128-bit arithmetic compute axis widths,
`coordinate_cardinality=product(widths)`, `register_width=max-min+1`, and
`placed_cardinality=coordinate_cardinality*register_width`. Validate in order:
axis bounds; coordinate maximum 1024; register width maximum 8; placed maximum
4096; ledger ceiling. Then reserve and enumerate. Collisions never refund.

SP0 also limits dimensions to 2, axis width to 7, voices to 4, intents to 8,
rhythm steps/material to 64, repeats to 8, sections to 4, total bars to 8, and
events to 2048.

## Cache, report, and failure contract

Cache keys include canonical input, algorithm, NumericContract, and profile
digests. Receipts replay atomically. A corrupt receipt raises
  `CACHE_RECEIPT_INVALID` in telemetry and is always ignored for a mandatory
  cold recomputation; it never directly fails compilation. Physical telemetry
never affects logical usage or artifact bytes.

Usage, child receipts, cache telemetry, and search statistics live in external
`CompileReport`, not Project or ResolvedChord. Stable errors are
`BUDGET_{STRUCTURAL,PLACED_DOMAIN,EXACT_ARITHMETIC,NUMERIC_EVAL,CHORD_SEARCH,
PAIR_RELATIONS,ORDERING,VALIDATION,EMITTED_EVENTS,TOTAL}_EXCEEDED`,
`BUDGET_CHILD_EXCEEDED`, `DOMAIN_CARDINALITY_OVERFLOW`,
`ARITHMETIC_COMPLEXITY_EXCEEDED`, and `CACHE_RECEIPT_INVALID`. Failure includes
stage, counter, requested, used, ceiling, optional child, snapshot, and
`partial_project:null`.

For `gen0-progression-exact-v1`, both root and progression-child `usage`
objects must contain `progression_states` and `progression_edges`; absence makes
a cached receipt `CACHE_RECEIPT_INVALID`. Other v1 profiles omit these optional
fields and semantically have zero progression use. Stable failures add
`BUDGET_PROGRESSION_STATES_EXCEEDED` and
`BUDGET_PROGRESSION_EDGES_EXCEEDED`. Atomic failure checks child leaf, root
leaf, then root total: the first two return the counter-specific code and the
last returns `BUDGET_TOTAL_EXCEEDED`; no counter changes on failure.

Required fixtures cover exact-ceiling/+1 for every counter, atomic
child/root/total failure, limb/cardinality boundaries, collision without refund,
cold/hit/corrupt cache parity, sort parity, no partial Project, shared versus
distinct domains, shuffled-input parity, and exhaustive-oracle winner equality.
The minimal direct-note and resolved-triad fixtures additionally publish their
complete logical opcode streams and receipts; optimized implementations must
replay those streams, not infer charges from physical calls.
